# リファクタ候補発見と issue 化

task: 全コードベースを分析してリファクタ候補を発見し、1責務 1 issue の粒度で GitHub issue として提案・作成する。

拡張思考を行いなさい。
**ultrathink**

CodexのAgent Teams機能を使って、以下の3つのチームメイトで並列分析を実施する。

## 設計の前提

- **このスキルは「発見と issue 化」までを担う。実装プランの策定は別スキル `/plan-issue` を使う**
- **1 RC（Refactor Candidate） = 1 責務 = 1 issue = 1 PR** が原則。まったく違う視点の差分を 1 issue にまぜない
- 全コードベース対象だが、全ファイルを Read するのは現実的でない。Glob/Grep で当たりを付け、怪しい場所だけ Read で深掘りする
- 規模が大きい場合は subagent (Explore) で範囲を分担する

## チーム構成

### チームメイトA: コードスメル / 規約違反

- 参照: `/.Codex/rules/coderule.md`、`/.Codex/rules/convention.md` セクション 2
- 観点: 関数長、ネスト深度、命名（`Manager`/`Util`/`Helper` 等の汎用語、単位なし数値、否定形 boolean）、try/catch 乱用（RULE-004）、class 使用（RULE-003）、不必要な useState / useEffect（RULE-009）、boolean props 過多（RULE-011）、複雑な条件式（RULE-013）、enum-like の if-else（RULE-006）、PascalCase 変数（RULE-008）等

### チームメイトB: 設計・アーキテクチャ負債

- 参照: `/.Codex/rules/convention.md` セクション 1, 2
- 観点: レイヤー違反（domain ↔ usecase ↔ infra の依存方向）、functional core / mutable shell の混在、責務の漏れ・重複（高凝集・疎結合違反）、循環依存、不適切な抽象化レベル、DRY/YAGNI/KISS 違反、層を跨ぐロジックの散らばり、値オブジェクト化されるべきプリミティブ、完全コンストラクタ違反

### チームメイトC: 死蔵コード / 老朽化

- 観点: 未使用の export、dead code（到達しないブランチ、コメントアウト残骸）、重複した型/関数定義、廃止された API の名残、未使用ファイル、古い設計パターンに引きずられた命名、放置された TODO/FIXME コメント、ドキュメントとコードのドリフト

## ワークフロー

### STEP 1: コードベース構造の把握

Glob でディレクトリ構造とファイル一覧を把握する。`packages/` 配下のサイズが大きい場合は subagent (Explore) を使って範囲を分担する。

NEVER: この時点では全ファイルを Read しない（コスト過大）。あくまで「どこを掘るか」の地図を作る段階。

把握すべき情報:

- パッケージごとのファイル一覧と粒度感
- 既存の関連ドキュメント（`docs/architecture.md`、`packages/*/docs/reading-guide.md`）から最新の設計意図
- 既存の `coderule.md` / `convention.md` の制約

### STEP 2: 並列分析

各チームメイトが担当観点で問題発見を行う。観点ごとに別々に subagent を立てて並列実行することを推奨する。

各検出について以下を記録する:

- **対象**: ファイルパス + 行範囲
- **現状コードの引用**（短く）
- **問題点**: なぜ問題か（該当ルール ID も明示）
- **提案する変更方針**: どう変えるか（実装詳細ではなく方向性レベル）
- **影響範囲**: 他にどのファイル/機能が影響を受けるか
- **推定規模**: S（数行〜1関数） / M（1ファイル全体〜数ファイル） / L（パッケージ横断 or アーキ変更）

NEVER: この時点でファイルを編集しない。分析と記録のみ。

### STEP 3: 統合と粒度調整（最重要ステップ）

全チームメイトの検出結果を統合する。**1責務 1 RC** の原則を厳格に適用する:

統合・分割ルール:

- **同じ責務に関する複数の検出は 1 つの RC に統合する**
  例: 「coach-loop.ts の関数 X が長すぎる」+「同じ X 内の命名が悪い」→ 1 RC
- **異なる責務をまたぐ検出は別 RC として分離する**
  例: 「coach-loop.ts のリファクタ」+「prompts.ts の命名統一」→ 2 RC
- **観点の異なる差分を 1 RC にまぜない**
  例: コードスメル修正と未使用 export 削除はファイルが同じでも別 RC
- **依存関係がある場合は明示する**
  例: RC-3 は RC-1 完了が前提（RC-1 で型を整理してから RC-3 で利用箇所を直す）

各 RC に以下を付与する:

- **RC-連番**（RC-1, RC-2...）
- **観点ラベル**: `[規約]` `[設計]` `[死蔵]`（複数該当する場合は主要なものを選ぶ）
- **推定規模**: S / M / L
- **依存**: 他 RC への参照（あれば）

ユーザーへの提示フォーマット:

```md
## RC-1 [設計] coach-loop の責務分離 (M)
**対象**: packages/core/src/coach-loop.ts (lines 200-340)
**現状**:
\`\`\`ts
function executeOneRound(...) { /* 100行以上 */ }
\`\`\`
**問題**: executeOneRound が capture/diff/AI/event 発火を一手に抱えており、責務が肥大化。convention.md §2「高凝集」違反。
**提案する方向性**: capture と AI 呼出を別関数に切り出し、executeOneRound はオーケストレーションに専念させる。
**影響範囲**: coach-loop.test.ts のモック対象が増える可能性。
**依存**: なし
```

そのうえで、各 RC についてユーザーの判断を求める:

- **採用** / **却下** / **修正**（粒度の分割・統合・方向性の修正）
- 採用された RC は次ステップ以降で issue 化する

### STEP 4: codex による第二意見

STEP3 の RC 一覧（ユーザーとの調整を経た最終版）について codex に意見を求める。チームメイトが見落とした候補や、粒度の不適切さを検証する。

codex を呼ぶときは timeout を延長すること。(7分以上を推奨)

```bash
codex exec -m gpt-5.4 "リファクタ候補のレビューをお願いします。瑣末な点への不要なリプライはするな。致命的な観点見落とし・粒度の不適切さ（1責務1issue原則違反）に尽力せよ。

候補一覧:
[RC-1, RC-2, ... を貼る]

(ref: AGENTS.md, .Codex/rules/coderule.md, .Codex/rules/convention.md)"
```

- codex が指摘した追加候補があれば RC-(N+1) として加え、ユーザーに再提示
- 粒度が不適切と指摘されたものは分割/統合してユーザー再提示
- codex が同意した RC のみを次ステップに進める
- ユーザー判断が必要な分岐があればループを止めて STEP 5 に進む

### STEP 5: issue 作成

ユーザーに承認された RC を `gh issue create` で GitHub に登録する。

issue テンプレート（既存 issue のスタイルに倣う。`gh issue list` で参考になるものを確認するとよい）:

```md
## 背景

[なぜこの refactor が必要か。現状のコードのどこに問題があるか。該当する coderule / convention のルール ID も明示]

## 現状

[該当箇所のファイルパスと行範囲、必要なら短いコード引用]

## 提案する方向性

[どう変えるか。**具体的な実装プランは `/plan-issue` で詰める前提なので、ここでは方向性レベル**で書く]

## やること

- [ ] [チェックボックス形式で TODO]
- [ ] [テスト追加 / 既存テスト修正の必要性]

## 影響範囲

[他にどのファイル/機能が影響を受けるか。下流への波及]

## 備考

- 推定規模: S / M / L
- 依存: 他 issue への参照（あれば）
- 関連ドキュメント: `docs/architecture.md` / `packages/*/docs/reading-guide.md` への参照
```

各 issue は **ひとつの責務** のみを扱う。複数観点の指摘を 1 issue にまぜない。タイトルは命令形で、対象パッケージ/ファイルが分かる形にする（例: `coach-loop.ts: executeOneRound の責務分離`）。

issue 作成後、URL 一覧をユーザーに報告する:

```md
作成した issue:
- RC-1: #42 (https://github.com/.../issues/42)
- RC-2: #43 (https://github.com/.../issues/43)
- ...
```

## NOTE

- このスキルは「発見と issue 化」までを担う。実装プランの策定は `/plan-issue`、実装後のレビューは `/code-review` を使う
- **1 RC = 1 issue = 1 PR の原則を厳格に守る**。複数観点の修正を 1 PR にまぜると review コストが跳ね上がるし、git history が読めなくなる
- 「全コードベース」と言っても全ファイルを Read する必要はない。Glob/Grep で当たりを付け、怪しい場所だけ Read で深掘りする
- subagent (Explore) を活用して並列で範囲を分担すると効率が良い。特に packages/core, packages/server, packages/client を別々に掘る
- TODO/FIXME コメントが既に書かれている箇所はコードベースが「ここに問題あり」と自己申告している場所。必ず拾う
- **ユーザーの承認なしに issue を作成しない**。STEP 3 でのフィードバック→STEP 4 codex →最終承認の流れを必ず踏む
