# ドキュメント最新化

task: コードリーディング補助用のドキュメントを全コードと照合し、古い記述・ドリフトを検出して正しく修正する。

拡張思考を行いなさい。
**ultrathink**

## 設計の前提

- **対象はコードリーディング補助用の .md ファイル**（reading-guide, architecture 等）。AGENTS.md やルールファイルは対象外
- **全コードとの照合**を行う（差分ベースではなく網羅的に検証する。差分だけ見ると既に古かった箇所を見落とす）
- ドキュメントの構造・スタイルは既存を踏襲する。勝手にフォーマットを変えない
- Mermaid 図がある場合は、コードの実態と一致しているかも検証対象に含める
- **修正は自動適用**する（ユーザー承認を個別に求めず、全修正を適用してから報告する）
- 修正後に codex のセカンドオピニオンを受ける

## ワークフロー

### STEP 1: 対象ドキュメントの発見

以下のパターンでプロジェクト内のドキュメントを探す:

```md
docs/**/*.md
packages/*/docs/*.md
```

見つかったファイルを一覧化する。ただし以下は除外する:

- `node_modules/`
- `.work/` (作業メモ)
- `AGENTS.md` / `.Codex/rules/*.md` / `.Codex/skills/**/*.md` (ルール・スキル定義)
- `docs/memory/` (プロジェクト思想。コードと直接対応しない)
- `docs/roadmap/` (ロードマップ。実装とは別の文脈)

### STEP 2: コードベースの現状把握

ドキュメントが参照しているコードの現在の姿を把握する。

- 各ドキュメントを読み、言及されているファイルパス・関数名・型名・定数名を抽出する
- それらが実際のコードに存在するか、Grep / Glob で確認する
- 存在しない場合はリネーム・削除・移動を追跡する（`git log --follow` 等）

NEVER: 全ファイルを Read するのはコスト過大。ドキュメントが言及しているファイルだけを Read する。

### STEP 3: ドリフト検出（並列推奨）

Agent Teams で並列に検出を行う。各チームメイトは担当ドキュメントのドリフトを網羅的に検出する。

ドキュメント数に応じて subagent を分担する。例:

- チームメイトA: `packages/core/docs/reading-guide.md`
- チームメイトB: `packages/server/docs/reading-guide.md`
- チームメイトC: `packages/client/docs/reading-guide.md` + `docs/architecture.md`

各チームメイトが検出すべきドリフトの種類:

#### 3-1. ファクト系ドリフト（最優先）

- **存在しない関数・型・定数への言及**: リネーム・削除されたものがドキュメントに残っている
- **シグネチャの変化**: 引数・戻り値が変わっているのに旧シグネチャで説明されている
- **コードブロックの陳腐化**: ドキュメント内のコード例が現在のコードと一致しない
- **ファイルパスの変化**: ファイルが移動・リネームされている

#### 3-2. 構造系ドリフト

- **新規ファイル・関数の欠落**: コードに追加されたがドキュメントに反映されていない
- **削除されたファイル・関数への言及**: コードから消えたのに説明が残っている
- **依存関係図の古さ**: import 構造が変わっているのに図が旧構造のまま

#### 3-3. 意味系ドリフト

- **設計意図の変化**: 「pause/resume で一時停止する」のように廃止された概念が説明されている
- **ワークフローの変化**: 処理フローが変わっているのに旧フローで説明されている
- **Mermaid 図との不整合**: 図中のノード名・矢印が現在のコードの呼び出し関係と一致しない

各検出項目について以下を記録する:

- **ドキュメント**: ファイルパス + 行範囲
- **ドリフト種別**: ファクト / 構造 / 意味
- **現状の記述**（引用）
- **コードの実態**（該当ファイルと行番号）
- **修正案**

### STEP 4: 修正適用

STEP 3 で検出した全ドリフトをドキュメントに反映する。

修正ルール:

- **既存のフォーマット・文体を踏襲する**。ドキュメントごとにスタイルが異なる場合がある（日本語 / 英語、箇条書き / 表形式、Mermaid の使い方等）。勝手に統一しない
- **更新日を書き換える**。ドキュメント冒頭に `> 最終更新: YYYY-MM-DD` がある場合は今日の日付に更新する
- **Mermaid 図はコードの実態に合わせて書き直す**。ただし見やすさのためのレイアウト工夫は維持する
- **新規セクションの追加は慎重に**。既存セクションの更新が主。新規ファイル/機能についてセクションを追加する場合は、周囲のセクションと同じ粒度・深さに合わせる
- **削除は最小限に**。廃止された概念の説明は「旧仕様」として注釈を残すか、完全削除するかはドキュメントの文脈に合わせて判断する

### STEP 5: セルフレビュー

修正後のドキュメントを通し読みし、以下を確認する:

- 修正によって文脈が壊れていないか（前後の文がつながるか）
- Mermaid 図の構文が正しいか（ノード名の引用符、矢印の方向）
- コード例のインデント・言語指定が正しいか
- 内部リンク（`[xxx](../yyy)` 等）が有効か

### STEP 6: codex セカンドオピニオン

修正後のドキュメント一覧を codex にレビューさせる。

codex を呼ぶときは timeout を延長すること。(7分以上を推奨)

```bash
codex exec "以下のドキュメントをレビューして。コードとの不整合、誤った説明、Mermaid図の構文エラーに尽力せよ。瑣末な文体指摘は不要。

対象:
[修正したドキュメントのファイルパス一覧]

照合先コード:
[ドキュメントが主に参照しているソースファイルのパス一覧]

(ref: AGENTS.md, .Codex/rules/coderule.md, .Codex/rules/convention.md)"
```

- codex の指摘があればドキュメントに反映する
- 文体やフォーマットの好み的指摘は無視してよい
- codex の指摘がなければ「追加の問題は検出されなかった」と報告する

### STEP 7: ユーザーへ報告

修正内容のサマリをユーザーに報告する。以下のフォーマットで:

```md
## ドキュメント更新サマリ

### [ファイルパス1]
- [修正1の要約]
- [修正2の要約]

### [ファイルパス2]
- [修正1の要約]

### 新規追加なし / 新規セクション追加あり
[あれば概要]

### codex レビュー結果
[指摘の有無と対応]
```

## NOTE

- このスキルは **既存ドキュメントの最新化** を担う。新規ドキュメントの作成は手動で依頼すること
- 「全コードとの照合」と言っても、全ファイルを Read するわけではない。**ドキュメントが言及しているファイル** を起点に、Grep / Glob で変化を追跡する
- ドキュメントの目的は「プロジェクトリーダーがコードを読む際の補助教材」であること。実装の詳細を網羅するのではなく、**読む順番・全体像・設計意図・落とし穴** に焦点を当てる
- Mermaid 図は読者の理解を助ける重要な要素。古い図は誤解を招くため、**ファクト系ドリフトと同等の優先度** で修正する
- `docs/roadmap/` や `docs/memory/` は対象外。これらはコードの実装状態ではなく、プロジェクトの方向性や思想を記述するもの
